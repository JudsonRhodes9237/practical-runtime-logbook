# How to Implement Feature Flag Management: Admin Panel CRUD for Incident Evidence

Short answer: build the admin panel around an append-only change record, then make create, list, toggle, and delete operations emit that record before they report success. For a marketplace, this costs more storage than keeping only current flag values, but it preserves the evidence needed to explain which seller, buyer cohort, or checkout path saw a change and who authorized it.

The UI is the easy part. The hard part is making the control plane answer an incident question six weeks later without turning customer IDs into metric labels or leaving cost ownership ambiguous. I've been paged by missed jobs and duplicate deliveries; the same runbook reflex applies here — every mutation needs an idempotency key, a durable outcome, and enough context to reconstruct intent.

Keep the invariant small: one accepted command produces at most one state transition and exactly one audit event.

## What should a Node.js and Next.js internal tool list, toggle, and delete for feature flags?

The panel should list the current state, version, scope, owner, and last change time. Its detail view should show the append-only event history. A toggle request should carry the version the operator saw and an idempotency key generated by the browser; a delete should be a retirement event, not immediate evidence destruction. A `409 Conflict` means the screen is stale, while replaying the same successful idempotency key returns the earlier result instead of applying the command twice.

That contract matters more than the choice of Node.js or Next.js. A thin Next.js page can call an internal JSON API, and a Node.js handler can implement the same state machine as the Go reference below. The example uses Go because the transition logic is easier to inspect in one file; the wire contract stays ordinary JSON.

Use separate records for desired state and history:

| Record | Mutable? | Incident value | Cost owner |
|---|---:|---|---|
| Flag snapshot | Yes, by version | What the control plane believed | Platform team |
| Change event | No | Who requested what, when, and why | Marketplace domain |
| Evaluation metric | Aggregated | Whether evaluation volume changed | Observability budget |

Don't put buyer IDs, seller IDs, request IDs, or flag values into metric labels. Prometheus instrumentation guidance warns that every unique label set creates another time series and advises keeping cardinality low. Put high-cardinality correlation data in the event record, where retention and access can be managed explicitly, and keep metrics bounded to fields such as operation and outcome.

## Implement the mutation boundary once

The following server is deliberately small, but it is runnable with Go 1.22 or later. It exposes a collection for create and list operations and an item path for toggle and retirement. The in-memory repository makes the behavior visible; replace it with a durable store whose transaction commits the snapshot, event, and idempotency result together before production use.

```go
package main

import (
	"encoding/json"
	"errors"
	"log"
	"net/http"
	"sort"
	"strings"
	"sync"
	"time"
)

type Flag struct {
	Key       string `json:"key"`
	Enabled   bool   `json:"enabled"`
	Scope     string `json:"scope"`
	Owner     string `json:"owner"`
	Version   int    `json:"version"`
	Retired   bool   `json:"retired"`
	ChangedAt string `json:"changed_at"`
}

type Command struct {
	Action         string `json:"action"`
	ExpectedVersion int   `json:"expected_version"`
	Actor          string `json:"actor"`
	Reason         string `json:"reason"`
}

type Event struct {
	FlagKey        string `json:"flag_key"`
	Action         string `json:"action"`
	Actor          string `json:"actor"`
	Reason         string `json:"reason"`
	Version        int    `json:"version"`
	IdempotencyKey string `json:"idempotency_key"`
	OccurredAt     string `json:"occurred_at"`
}

type Store struct {
	mu      sync.Mutex
	flags   map[string]Flag
	events  []Event
	replays map[string]Flag
}

var errConflict = errors.New("version conflict")

func (s *Store) apply(key, idem string, cmd Command) (Flag, error) {
	s.mu.Lock()
	defer s.mu.Unlock()
	if idem == "" {
		return Flag{}, errors.New("idempotency key required")
	}
	if prior, ok := s.replays[idem]; ok {
		return prior, nil
	}
	now := time.Now().UTC().Format(time.RFC3339Nano)
	flag, exists := s.flags[key]
	if cmd.Action == "create" {
		if exists || cmd.ExpectedVersion != 0 {
			return Flag{}, errConflict
		}
		flag = Flag{Key: key, Scope: "marketplace", Owner: "checkout", Version: 1, ChangedAt: now}
	} else {
		if !exists || flag.Version != cmd.ExpectedVersion || flag.Retired {
			return Flag{}, errConflict
		}
		flag.Version++
		flag.ChangedAt = now
		switch cmd.Action {
		case "toggle":
			flag.Enabled = !flag.Enabled
		case "retire":
			flag.Retired = true
		default:
			return Flag{}, errors.New("unsupported action")
		}
	}
	s.flags[key] = flag
	s.events = append(s.events, Event{
		FlagKey: key, Action: cmd.Action, Actor: cmd.Actor, Reason: cmd.Reason,
		Version: flag.Version, IdempotencyKey: idem, OccurredAt: now,
	})
	s.replays[idem] = flag
	return flag, nil
}

func writeJSON(w http.ResponseWriter, status int, value any) {
	w.Header().Set("Content-Type", "application/json")
	w.WriteHeader(status)
	if err := json.NewEncoder(w).Encode(value); err != nil {
		log.Printf("encode response: %v", err)
	}
}

func main() {
	store := &Store{flags: map[string]Flag{}, replays: map[string]Flag{}}
	mux := http.NewServeMux()
	mux.HandleFunc("GET /internal/flags", func(w http.ResponseWriter, r *http.Request) {
		store.mu.Lock()
		defer store.mu.Unlock()
		flags := make([]Flag, 0, len(store.flags))
		for _, flag := range store.flags {
			flags = append(flags, flag)
		}
		sort.Slice(flags, func(i, j int) bool { return flags[i].Key < flags[j].Key })
		writeJSON(w, http.StatusOK, flags)
	})
	mux.HandleFunc("POST /internal/flags", func(w http.ResponseWriter, r *http.Request) {
		var cmd Command
		if err := json.NewDecoder(r.Body).Decode(&cmd); err != nil || cmd.Action != "create" {
			http.Error(w, "invalid create command", http.StatusBadRequest)
			return
		}
		key := strings.TrimSpace(r.URL.Query().Get("key"))
		idem := r.Header.Get("Idempotency-Key")
		if key == "" || idem == "" || cmd.Actor == "" || cmd.Reason == "" {
			http.Error(w, "key, actor, reason, and idempotency key are required", http.StatusBadRequest)
			return
		}
		flag, err := store.apply(key, idem, cmd)
		if err != nil {
			http.Error(w, err.Error(), http.StatusConflict)
			return
		}
		writeJSON(w, http.StatusCreated, flag)
	})
	mux.HandleFunc("PATCH /internal/flags/{key}", func(w http.ResponseWriter, r *http.Request) {
		var cmd Command
		if err := json.NewDecoder(r.Body).Decode(&cmd); err != nil || cmd.Actor == "" || cmd.Reason == "" {
			http.Error(w, "valid command, actor, and reason are required", http.StatusBadRequest)
			return
		}
		flag, err := store.apply(r.PathValue("key"), r.Header.Get("Idempotency-Key"), cmd)
		if err != nil {
			http.Error(w, err.Error(), http.StatusConflict)
			return
		}
		writeJSON(w, http.StatusOK, flag)
	})
	mux.HandleFunc("DELETE /internal/flags/{key}", func(w http.ResponseWriter, r *http.Request) {
		var cmd Command
		if err := json.NewDecoder(r.Body).Decode(&cmd); err != nil {
			http.Error(w, "invalid retire command", http.StatusBadRequest)
			return
		}
		cmd.Action = "retire"
		flag, err := store.apply(r.PathValue("key"), r.Header.Get("Idempotency-Key"), cmd)
		if err != nil {
			http.Error(w, err.Error(), http.StatusConflict)
			return
		}
		writeJSON(w, http.StatusOK, flag)
	})
	log.Fatal(http.ListenAndServe(":8080", mux))
}
```

There are two details I wouldn't waive in review. First, an empty idempotency key must be rejected on every mutation; the shared `apply` boundary enforces that even if a handler misses the check. Second, authorization identity must come from a verified session rather than trusting the JSON `actor` field. The field remains in the example to make the evidence shape obvious, not as an authentication design.

The production transaction is the real boundary. If the database commits the flag but not its audit event, the panel can change customer behavior while deleting the explanation. If it commits the event but not the flag, an investigator sees intent that never took effect. Neither is acceptable. Use one atomic transaction, constrain `(flag_key, version)` to be unique, and constrain the idempotency key to be unique within the calling principal's scope.

## How can retained flag evidence preserve cost attribution?

For a marketplace, assign every event to a stable domain such as checkout, catalog, or seller onboarding; use that domain for storage accounting and retention policy. Record the flag key, old and new versions, requested action, verified actor, reason, timestamp, and idempotency key. Don't copy whole customer payloads into the event. They expand storage, complicate access, and blur which team owns the bill.

Retention should follow the reconstruction window, not an arbitrary desire to keep everything. I'm not sure what that window should be for a particular marketplace; incident review needs, internal policy, and applicable obligations decide it. Resolve the uncertainty before launch, document the deletion schedule, and test that an event remains queryable until its scheduled expiry.

Metrics answer a narrower question. Count commands by bounded `operation` and `outcome`, measure command duration, and track the age of the last successful audit persistence. Logs can carry a correlation token that joins a request to the durable event. Prometheus explicitly cautions against labels with unbounded cardinality, so `customer_id`, `flag_key`, `actor`, and `idempotency_key` belong outside metric labels even though they may be essential evidence elsewhere.

Measure less.

Start with failure-oriented tests, not screenshots. Submit the same toggle twice with one idempotency key and assert one version increment. Submit two different commands against version 7 and assert that only one commits while the other receives `409`. Retire a flag, verify it disappears from the default active list, then verify its snapshot and event history remain available to an authorized investigator. Exercise an expired-event fixture so the deletion policy is observable rather than aspirational. Then run the reconstruction from the other direction: begin with a time range and a customer-facing symptom, locate the bounded operational signal, follow its correlation token to the durable event, identify the version that took effect, and confirm which marketplace domain owns the retained bytes. This longer path catches a common design error: collecting individually useful fields without preserving a practical way to join them during an incident.

Run those checks in the repository's existing CI workflow. GitHub Actions can automate repository workflows, so it is a reasonable place to compile the server, run race-enabled Go tests, and execute contract tests for the Node.js or Next.js client. The deployment gate should fail if the client expects a field or status code the control plane no longer supplies.

An operational drill closes the gap that unit tests leave. Give the on-call engineer only a customer incident time range and a flag key, then ask for the authorized actor, command reason, affected version, and domain charged for retained evidence. If the answer requires querying raw metric labels or guessing from the latest snapshot, the design isn't ready.

## Know when this design is the wrong fit

The catch is storage and control-plane complexity. Append-only events plus snapshots consume more space, require retention work, and make mutation handling transactional. This design is not suitable when flags are compile-time constants, no runtime operator can change them, and deployment history already provides the complete evidence trail. Stick with version-controlled configuration in that case.

It is also insufficient for flag evaluation analytics. The admin trail proves who changed control-plane state; it doesn't prove that every application instance evaluated the same value for every request. When that distinction matters, add separately budgeted evaluation telemetry with sampling or aggregation, and keep its retention decision separate from the administrative audit trail. Your mileage may vary because request volume and reconstruction requirements determine whether per-evaluation evidence is defensible.

For runtime marketplace flags, the decision rule is direct: adopt the design only if reconstructing an incident is worth the durable event storage, transaction boundary, and access controls. If it is, charge that evidence to an explicit domain and test the reconstruction path before the first toggle reaches production.
